# AGENTS.md

This file is for everyone who changes the PHP Stellar SDK, people and agents alike. It holds what the tree does not show: the commands, what "done" means, which files are generated, the conventions that differ from PHP defaults, and the limits of a change. When this file and a file it names disagree, the named file wins, and the pull request that changes the fact updates this file. Users of the SDK read `README.md` and `docs/`; agents that build on the SDK read the skill under `skills/`.

## Commands

Setup is described in `CONTRIBUTING.md`. The CI matrix in the tests workflow names the tested PHP versions.

```sh
composer install --prefer-dist --no-progress
php -d memory_limit=-1 vendor/bin/phpunit --testsuite unit --no-coverage
vendor/bin/phpunit --no-coverage --filter testFromSeed Soneso/StellarSDKTests/Unit/Crypto/KeyPairTest.php
php -d memory_limit=-1 vendor/bin/phpunit --testsuite generated --no-coverage
composer analyse
```

- The unit suite (about 9,000 tests) runs in under 10 seconds and needs no network. Pass `php -d memory_limit=-1`, because the suite exceeds PHP's default limit of 128 MB and the Composer scripts `composer test` and `composer test:coverage` inherit that limit. Pass `--no-coverage`, because `phpunit.xml` configures coverage and a loaded Xdebug otherwise turns a passing run into exit 1.
- The `generated` suite holds the generated XDR tests; the `integration` suite runs against live testnet and futurenet, is not part of CI, and needs the pcntl extension for the streaming tests:

```sh
php -d memory_limit=-1 vendor/bin/phpunit --testsuite integration --no-coverage
```

- `composer analyse` is PHPStan level 6 over `Soneso/StellarSDK/` with the generated files excluded; its parallel workers need loopback sockets.
- Local coverage runs through Xdebug and takes about 90 seconds; CI collects coverage with PCOV:

```sh
XDEBUG_MODE=coverage php -d memory_limit=-1 vendor/bin/phpunit --testsuite unit --coverage-clover coverage/clover.xml
```

- The API documentation builds with `composer docs` in about a minute and writes the gitignored `docs/api/` and `.phpdoc/`; `composer docs:clean` removes both. CI publishes `docs/api/` from `main`.
- There is no formatter or linter configuration in the repository.

## Definition of done

Before reporting a change as done:

1. The unit suite and `composer analyse` pass. The `generated` suite passes when the XDR generator, an override file, or the XDR definitions changed.
2. Area gates. After a generator change: `make xdr-generator-test` and `make xdr-validate`. After a change to `xdr/*.x`, to the SEP-51 fixtures or to the generated tests: `make xdr-update`, because CI's drift check does not watch those paths. After a matrix generator change: `python3 -m unittest discover -s tools/matrix-generator/tests`. After a change to SEP-51 JSON emission: `bash tools/sep-51-test-fixtures/refresh_corpus.sh`.
3. A test that would fail without the change exists. A bug fix starts with the failing test.
4. `CHANGELOG.md` has an entry under `[Unreleased]` in the Keep a Changelog section the change belongs to (Added, Changed, Deprecated, Removed, Fixed, Security), in present tense, one entry per user-visible change.
5. No generated file was edited by hand. The user documentation under `docs/` and the skill under `skills/` describe the released SDK; they change on the `release-docs` branch with the release. `docs/documentation-strategy.md` is a process document and changes in the pull request that changes a fact it states.

Every pull request runs `.github/workflows/tests.yml` (unit suite per PHP version, PCOV coverage, Codecov upload), `.github/workflows/static-analysis.yml` and `.github/workflows/dependency-audit.yml` (`composer audit --no-dev --abandoned=report`). The `agents-md-paths` job of the tests workflow runs `.github/scripts/check_agents_md_paths.py`, which fails when a path this file names does not exist, so a change that moves a file also changes the line here. `.github/workflows/xdr-generator.yml` runs when its path filter matches and fails on regenerated types, PHPStan list, or SEP-51 tests that differ from the committed files. The branch rules require the Codecov project status; `codecov.yml` holds the targets and the ignore list.

## Generated code and data

Generated files are never edited by hand. Change the generator or its override files and regenerate.

- **XDR types.** The files in `Soneso/StellarSDK/Xdr/` whose header says they were generated by xdrgen, `tools/xdr-generator/phpstan-generated.neon`, the generated test files in `Soneso/StellarSDKTests/Unit/Xdr/Generated/` and the files in `Soneso/StellarSDKTests/Unit/Xdr/Sep51/` that carry the generator header. The files in `Soneso/StellarSDK/Xdr/` without the header are hand-written: the wrappers that extend the generated `Soneso/StellarSDK/Xdr/*Base.php` classes and the helper classes `XdrBuffer`, `XdrEncoder`, `XdrDecoder` and `TxRepHelper`. A hand-written file there never carries the generator header, because `make xdr-clean-generated` deletes by header. The stellar-xdr commit is pinned as `XDR_COMMIT` in `Makefile`; the definitions in `xdr/` are tracked copies of that commit and are never edited, `make xdr-update` re-downloads them. The nine override files are the `tools/xdr-generator/generator/*_overrides.rb` files, `tools/xdr-generator/generator/cat_a_inline_targets.rb` and `tools/xdr-generator/generator/txrep_types.rb`. `make xdr-update` needs Docker, network, host Ruby, and an installed `vendor/`, and takes about five minutes; it leaves a clean tree when the committed output is current. Run `make xdr-generator-update-snapshots` only after an intended output change, and read the snapshot diff. Before changing the generator, an override file, or the pin, read `tools/xdr-generator/README.md`; it describes the override files and the base-and-wrapper pattern.
- **SEP-51 conformance.** `tools/sep-51-test-fixtures/oracle-pin.json` pins the reference CLI and its install command. `tools/sep-51-test-fixtures/corpus.json` is generated from `tools/sep-51-test-fixtures/_corpus_seed.php` by `tools/sep-51-test-fixtures/generate_corpus.py` and checked offline by the unit suite. Every regeneration rewrites the `generated_at` field, so restore the file when no entry changed. A fixture the reference cannot resolve needs an `oracle_incomparable` entry with its reason. Before adding a fixture, changing JSON emission, or bumping the pin, read `tools/sep-51-test-fixtures/README.md`; it holds the fixture format and the refresh procedure.
- **Compatibility matrices.** The files under `compatibility/` describe the released SDK. Every generator run rewrites their `Generated` line and the SEP matrices cite source line numbers, so a run that only verifies a change restores `compatibility/` before the commit. The matrices change in four cases. An SDK behavior change ships them with its release. A generator fix commits them in its pull request, after the maintainer has read every changed cell. A new protocol version adds its rows when it is live. A mixed diff is the maintainer's decision. The generators need network; a GitHub token in `GITHUB_TOKEN` raises the API rate limit. The RPC data under `tools/matrix-generator/rpc/data/` is gitignored. Before changing a generator or an analyzer, read `tools/matrix-generator/README.md`; it holds the pipelines and their inputs.
- **Agent skill.** `skills/stellar-php-sdk/references/api_reference.md` is generated by reflection with `php tools/skill-generator/generate_api_reference.php`. Its output on `main` includes unreleased API, so it is regenerated at release only, together with the skill version and the zip; a verification run restores the committed file. Before changing the reference generator, read `tools/skill-generator/README.md`; it holds the scan rules.
- **Test fixtures.** The six files under `Soneso/StellarSDKTests/bindings/` were generated by the external `stellar_contract_bindings` tool and are not edited. The wasm files under `Soneso/StellarSDKTests/wasm/` are test inputs; only the P28 owner fixture has its source in the repository, under `tools/p28-owner-fixture/`, replicated in four SDK repositories. Before changing it, read `tools/p28-owner-fixture/README.md`; it holds the build and the replication rule.

## Conventions and gotchas

- PHPUnit is strict: a test that prints output is risky and fails the run (`phpunit.xml`).
- Unit tests mock HTTP with Guzzle's `MockHandler`, injected through `setHttpClient`, `setMockHandler` or `setMockHandlerStack`; no unit test reaches a network. Integration tests pick their network per class with `$testOn`.
- A new unit test declares `strict_types=1`, so a wrong scalar type in test code is an error.
- `phpstan-baseline.neon` lists known findings. An entry without a matching finding fails `composer analyse`, so fixing a baselined finding removes its entry.
- Public classes and methods carry PHPDoc blocks with `@param`, `@return`, `@throws` and `@see` where they apply; the API documentation is generated from them. Comments describe current behavior and its reason, never history.
- New code uses the typed API; raw XDR appears only where no typed path exists, because the typed layer carries the validation and the documentation users read.

## Boundaries

- Releases are the maintainer's. Outside a release preparation the maintainer directs, an agent never changes `VERSION_NR` in `Soneso/StellarSDK/StellarSDK.php`, the skill version fields in `skills/stellar-php-sdk/SKILL.md`, `skills/.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json`, the zip `skills/stellar-php-sdk.zip`, a tag, a GitHub release, or the Packagist package.
- No credential lives in the repository. CI uses OIDC for the Codecov, Pages, and SBOM uploads. Ask before adding a dependency, a workflow, or a new generated artifact; each is a maintenance commitment the maintainer carries after the pull request.

## Changes

- Branch from `main` with a short kebab-case name that names the change; open the pull request against `main`.
- The commit subject is one imperative sentence of at most 72 characters without a type prefix; the body states the motivation and what the change does, so the log reads without the diff. The pull request body follows the same form and names what was verified.
- A pull request carries code, tests, and the CHANGELOG entry.

## Where details live

- Before your first change, read `CONTRIBUTING.md`; it holds setup, how to report a bug or propose a feature, how a change is submitted and what the review checks.
- Before writing or changing a page under `docs/`, read `docs/documentation-strategy.md`; it holds the page template, the example rules, and the release policy for documentation.
- Before touching the skill under `skills/`, read `skills/README.md` and `tools/skill-generator/README.md`; they hold the skill's structure and the reference generator.
- Before changing a tool under `tools/`, read its README; every tool directory has one.
