# Migrating to 1.16.0

This guide covers the observable changes between 1.15.0 and 1.16.0. If you upgrade from an older version, also review the CHANGELOG between your version and 1.15.0. Each note describes one situation: whether you are affected, how it shows, and what to do.

## Contract arguments

- If you pass a muxed account (`M...`) or muxed contract (`W...`) address to an `Address` parameter of `ContractSpec::nativeToXdrSCVal` or `funcArgsToXdrSCValues`: 1.16.0 throws `InvalidArgumentException` with `Address takes an account (G...) or contract (C...) address, got <address>: a muxed address needs a MuxedAddress parameter`. In 1.15.0 an `Address` parameter accepted an `M...` strkey and any `Address` object. Pass the underlying account or contract address; for a `W...` address, `MuxedContract::fromAddress($address)->getContractId()` returns it. `MuxedAddress` parameters keep accepting muxed addresses.

  ```php
  // 1.15.0
  $args = $spec->funcArgsToXdrSCValues('balance', ['id' => $muxedAccountId]);
  ```

  ```php
  // 1.16.0
  use Soneso\StellarSDK\MuxedAccount;

  $accountId = MuxedAccount::fromAccountId($muxedAccountId)->getEd25519AccountId();
  $args = $spec->funcArgsToXdrSCValues('balance', ['id' => $accountId]);
  ```

- If you pass a claimable balance or liquidity pool `Address` object to an `Address` or `MuxedAddress` parameter of `ContractSpec::nativeToXdrSCVal` or `funcArgsToXdrSCValues`: 1.16.0 throws `InvalidArgumentException` whose message names the parameter type and the address and ends with `is produced by the host and is not a contract input`. In 1.15.0 an `Address` parameter encoded such an object unchecked. Pass an account (`G...`) or contract (`C...`) address.

- If you build an `XdrSCVal` by hand for a `MuxedAddress` parameter, such as the `to` argument of a Stellar Asset Contract `transfer`: 1.16.0 converts `G...`, `M...`, `C...` and `W...` strings and the corresponding `Address` objects for that parameter type. In 1.15.0 a `MuxedAddress` parameter threw `InvalidArgumentException` for every string and every `Address` object. Pass the strkey or the `Address` object; a prebuilt `XdrSCVal` still passes through unchanged.

- If you build maps with `XdrSCVal::forMap`, or pass maps or map-encoded structs through `ContractSpec`: 1.16.0 orders the entries by the Soroban host's key order and throws `InvalidArgumentException` with `Duplicate SCMap key (XDR base64): <key>` for keys equal in host order. In 1.15.0 the entries kept their insertion order, and the host rejected arguments whose keys were out of its order. Supply distinct keys. Code that reads the entries of a built map gets them in host order; decoded maps keep their wire order.

## Soroban authorization

- If you sign authorization with a muxed account (`M...`) or muxed contract (`W...`) address as the credential address, `forAddress` target, or delegate: 1.16.0 throws `InvalidArgumentException` whose message starts with `Muxed account (M...) and muxed contract (W...) addresses are not valid Soroban` and names the address. `AssembledTransaction::signAuthEntries` throws before it writes an expiration or calls your callback. In 1.15.0 a muxed credential address was signed without a check, and an `M...` target or delegate failed with other messages. Use the underlying `G...` or `C...` address.

- If you pass `validUntilLedgerSeq` to `AssembledTransaction::signAuthEntries`, or `signatureExpirationLedger` to `SorobanAuthorizationEntry::sign`, for an entry that already carries a signature on any node: 1.16.0 throws `InvalidArgumentException` with `Signature expiration ledger <requested> conflicts with stored ledger <stored>` when the value differs from the stored expiration. In 1.15.0 the call overwrote the expiration, so the earlier signatures did not match the new payload and the host rejected the entry. Omit the expiration for every signer after the first.

  ```php
  // 1.15.0
  $tx->signAuthEntries($secondSigner, validUntilLedgerSeq: $expirationLedger);
  ```

  ```php
  // 1.16.0
  $tx->signAuthEntries($secondSigner);
  ```

- If you call `AssembledTransaction::signAuthEntries` without `validUntilLedgerSeq`: 1.16.0 keeps the stored expiration of an entry that already carries a signature. It fetches the latest ledger at most once per call, and only when an unsigned matching entry needs the default of the latest ledger plus 100. In 1.15.0 every such call fetched the latest ledger and wrote a fresh expiration to every matching entry, which invalidated earlier signatures. Live code needs no change. In tests with a mocked HTTP client, queue a `getLatestLedger` response only for calls that sign an unsigned entry.

- If you inspect or retry the transaction's auth entries after `AssembledTransaction::signAuthEntries` threw, for example from your signing callback: in 1.16.0 the entries are unchanged, because the method signs copies and replaces the transaction's entries only after it has signed every matching entry. In 1.15.0 the method changed the transaction's entries one by one, so the entries handled before the failure kept their new expiration and signatures. Retry the call on the same transaction without restoring the entries first.

- If you build unsigned auth entries with an empty vector (`XdrSCVal::forVec([])`) as the signature placeholder: 1.16.0 counts such a node as unsigned, like a void one. `needsNonInvokerSigningBy` lists its address, `signAuthEntries` signs it, and `AssembledTransaction::sign` throws `Exception` with ``Transaction requires signatures from multiple signers. See `needsNonInvokerSigningBy` for details.`` while an account node holds it. In 1.15.0 such a node counted as signed: `needsNonInvokerSigningBy` skipped it, `signAuthEntries` without a callback threw for its signer, and `sign` did not stop on it. Sign every listed account before you call `sign`; `XdrSCVal::forVoid()` and an empty vector behave the same.

- If you call `AssembledTransaction::sign` on a transaction with an `ADDRESS_WITH_DELEGATES` entry whose top-level account (`G...`) has no signature while its delegates sign: 1.16.0 throws `Exception` with ``Transaction requires signatures from multiple signers. See `needsNonInvokerSigningBy` for details.`` In 1.15.0 `sign` accepted the entry when every delegate node carried a signature or the entry had no delegate nodes, and the host rejected the transaction, because an account authenticates with the signatures of its own node. Sign the top-level account node as well. A custom account contract (`C...`) at the top level never blocks `sign`.

## PHP version

- If your project runs on PHP 8.0: Composer does not install 1.16.0, which declares `php >=8.1`, and resolves a constraint such as `^1.15` to 1.15.0. In 1.15.0 the floor was PHP 8.0. Move the project to PHP 8.1 or higher to receive 1.16.0, or stay on 1.15.0 until you do.

## XDR

- If you dispatch over `XdrSCAddressType`, `Address` types, or `XdrContractCostType` values without a default branch: 1.16.0 decodes `SC_ADDRESS_TYPE_MUXED_CONTRACT` (5), returned as `Address::TYPE_MUXED_CONTRACT` by `XdrSCVal::toNative`, and the cost types `MlDsa44DecodeVerifyingKey` (86) through `VerifyMlDsa87Sig` (94). A `match` without `default` throws `UnhandledMatchError` on them, and a `switch` without `default` skips them. In 1.15.0 decoding these values threw `InvalidArgumentException` with `Unknown enum value: <value>`. Add branches for the new values.

- If you dispatch over `XdrStellarValueType` values or read the arms of `XdrStellarValueExt`: 1.16.0 decodes `STELLAR_VALUE_SIGNED_MS` (3) and `STELLAR_VALUE_EMPTY_TX_SET_MS` (4), with the arms `signedMsValue` and `proposedMsValue` that carry `closeTimeMs`. In 1.15.0 decoding these values threw `InvalidArgumentException` with `Unknown enum value: <value>`. Add branches for the new members. Existing members, arms, and XDR-JSON keys keep their meaning.

## Liquidity pools

- If you construct `AssetTypePoolShare` from two credit assets of the same type and code, or decode such a pool share with `Asset::fromXdrChangeTrustAsset`: 1.16.0 orders the issuers by their raw 32-byte public keys, as stellar-core does, and throws `RuntimeException` with `Assets <assetA> and <assetB> are in wrong order. Sort by type, code bytes, then raw issuer public key bytes.` for a reversed pair. In 1.15.0 the SDK compared the issuer strkeys as text, which orders some pairs the other way. Order such a pair by the decoded issuer keys.

  ```php
  // 1.15.0
  if (strcmp($assetA->getIssuer(), $assetB->getIssuer()) > 0) {
      [$assetA, $assetB] = [$assetB, $assetA];
  }
  $poolShare = new AssetTypePoolShare($assetA, $assetB);
  ```

  ```php
  // 1.16.0
  use Soneso\StellarSDK\Crypto\StrKey;

  if (strcmp(StrKey::decodeAccountId($assetA->getIssuer()), StrKey::decodeAccountId($assetB->getIssuer())) > 0) {
      [$assetA, $assetB] = [$assetB, $assetA];
  }
  $poolShare = new AssetTypePoolShare($assetA, $assetB);
  ```

## Soroban RPC

- If you read `diagnosticEventsXdr` from the `TransactionInfo` objects of `SorobanServer::getTransactions`, or build `TransactionInfo` from test data with a `diagnostic_events` key: 1.16.0 reads the `diagnosticEventsXdr` key that stellar-rpc sends, so the property holds the server's diagnostic events, and a `diagnostic_events` key leaves it null. In 1.15.0 the SDK read `diagnostic_events`, so the property stayed null for server responses. Read the property directly, and rename the key in your test data to `diagnosticEventsXdr`.
